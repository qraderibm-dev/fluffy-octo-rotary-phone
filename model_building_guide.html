0 TL;DR

The whole project on one screen: the constraint, the build, the measured outcome, and the lesson worth carrying into the next model.

Problem

Annotate audio, not vibes

Annotate 15-second audio clips into a strict 15-field JSON using the Meeami Brioche 28-Class taxonomy. Constraints: zero budget, 6-person team, 900 clips/day, laptop had 8 GB RAM, no GPU.

$0 budget 6-person team 900 clips/day 8 GB RAM No GPU

Built

A teacher, a student, and a hard output contract

Fine-tuned Qwen 2.5 3B Instruct using QLoRA on 538 verified examples generated by a larger teacher model (NVIDIA NIM). Exported to GGUF, deployed via llama-server for local inference.

Qwen 2.5 3B QLoRA · rank 32 538 examples GGUF Q4_K_M llama-server

Outcome

Production-quality on a closed-vocabulary task

100% on 73-case exhaustive coverage suite (28 classes, 4 environments, multi-event, silence)

~84% on 107-case novel-phrasing regression (real ceiling ~92% because NIM ground truth is ~92% accurate)

Runs offline at 7–8 tokens/sec on CPU, ~15–30s per annotation

Artifact kept private; this guide documents the build without redistributing weights

Transferable lesson

For narrow, structured, closed-vocabulary tasks, fine-tuning a small model (0.5B–3B) on teacher-generated data with grammar constraints and deterministic postprocessing can approach production quality without a big model or a big budget. The bottleneck is always data quality, not model size. Better data on a 3B beats bad data on a 7B.

1 The original problem

This was not a creative writing task. It was a contract: one raw description in, one exact 15-field object out. Every field had a definition, and every completion had to pass review.

The task

Convert a short text description like hum indoor env into a strict 15-field JSON annotation using the Meeami Brioche 28-Class taxonomy.

The 15 fields

All fifteen fields had to be present, in order. The order itself was part of the output contract.

  1. 01sound_events
  2. 02activity_from_sound
  3. 03activity_from_speech
  4. 04acoustic_environment
  5. 05speech_presence
  6. 06speaker_count
  7. 07speech_analysis
  8. 08non_speech_vocalizations
  9. 09animal_present
  10. 10animal_sounds
  11. 11music_detected
  12. 12media_sound_detected
  13. 13caption
  14. 14detail
  15. 15Brioche_Class_Label

Hard constraints

  • The Brioche_Class_Label must use exactly one or more of 28 predefined taxonomy strings.
  • Multiple labels allowed (multi-label classification).
  • Environment field has exactly 4 possible values: indoor-quiet, indoor-noisy, outdoor-natural, outdoor-urban.
  • Speech, animal, music, and media flags are Yes / No.
  • Free-text caption and detail must follow template rules.

The three requirements that made this hard

1

Strict structure

Valid JSON, all 15 fields, in order.

2

Taxonomy conformance

Only 28 valid class strings, no typos or invented classes.

3

Semantic accuracy

Pick the correct class for each event. Don’t confuse dog-whining with dog-barking. Don’t confuse media playback with music.

Failure condition

Any of these three failing means the annotation fails review. A structurally valid object with the wrong event label is still a failed annotation.

Original attempted architecture — and why it failed

Every clip → Full 12,500-token system prompt → Hosted API → Tokens + rate limits

The first architecture sent the full 12,500-token system prompt to a hosted API for every clip. This burned tokens and hit rate limits. Re-sending static content 900 times per day is what made hosted APIs impractical.

That is an economic problem before it is a model-quality problem. The taxonomy is static; paying to upload it on every request is an avoidable cost.

Q1

RAG vs Fine-tuning vs Distillation vs Prompting?

RAG

Rejected

What: Retrieve relevant documents from a corpus at query time.

Use when: Knowledge is large, changing, factual, or per-query.

Do NOT use when: The task is behavior, format, or classification — not knowledge retrieval.

In this project: Rejected. The task is classification into a fixed taxonomy, not knowledge lookup. There is no corpus to retrieve from. The “knowledge” is the taxonomy itself, which fits in a prompt.

Fine-tuning

Conditional

What: Train additional weights on labeled examples to shift behavior.

Use when: The task requires a strict format, style, or behavior that prompts can’t reliably enforce.

Do NOT use when: You only need to change what the model knows — use RAG.

In this project: Chosen, but only after prompt + grammar + postprocess failed to close the gap on small models.

Distillation Chosen

Teacher → student

What: Generate examples from a large teacher model, then train a small student on them.

Use when: The teacher is excellent at the task and you need the student to run on cheap hardware.

Risk: The student inherits the teacher’s mistakes. Validate before training.

In this project: NIM (Nemotron 3.5 Bolt) was the teacher, Qwen 2.5 3B was the student. 538 teacher-generated examples.

Prompting alone

Insufficient here

What: Same model, better instructions.

Use when: The task is simple, the model is large enough (7B+), and budget is not a constraint.

When it fails: When constraints compete for the model’s limited capacity.

In this project: Failed on models below 3B. Grammar constraints fix structure but not semantics.

Decision → Why

Chosen: teacher distillation, then QLoRA fine-tuning. RAG was rejected because there is no knowledge corpus — only a fixed taxonomy that fits in a prompt. Prompting alone failed below 3B, and grammar constraints repaired the structure without repairing the meaning. NIM supplied the teacher signal; 538 examples taught Qwen 3B the behavior; postprocess handled the deterministic residual.

Q2

What model size do I need?

Rough rule for structured annotation tasks:

0.5B

Cannot hold a 28-class taxonomy reliably. Useful only with strict grammar + postprocess. Expect 3–5/10 semantic accuracy.

Too small
1.5B

Better format adherence, still weak on taxonomy nuances. Expect 5–7/10.

Fragile
3B

Sweet spot for narrow tasks. Can hold ~30 classes in context with training. Expect 8–10/10 with grammar + postprocess + fine-tuning.

Chosen
7B

Handles larger taxonomies (50–100 classes). Good without fine-tuning for many tasks. Needs 8+ GB RAM or a GPU.

Feasible
13B–70B

General-purpose reasoning, coding, multi-step. For classification tasks, generally overkill unless the task is genuinely complex.

Overkill here

In this project: We tried 0.5B → 1.5B → 3B in sequence. Each step up improved accuracy meaningfully. Qwen 3B was the smallest model that could hold the 28-class taxonomy reliably.

!

Key insight: Better data on a 3B beats mediocre data on a 7B. Never skip the data-quality step.

Decision → Why

Chosen: Qwen 2.5 3B, the smallest model that held all 28 classes. A 7B did not fit comfortably in the laptop’s usable memory, while 0.5B and 1.5B failed on class coverage. The 3B size was large enough for the taxonomy and small enough to run quantized on an 8 GB CPU-only machine.

Q3

How do I enforce strict output format?

Three layers, applied together. Each layer addresses a different class of failure.

01

Prompt

Describe the format in the system prompt.

Only works well on 7B+ models. Fails ~20–40% of the time on 3B and below.

02

Grammar-constrained decoding

GBNF / JSON schema physically prevents the model from emitting invalid tokens. 100% structural compliance. No retries needed.

Use when: You need valid JSON or exact enum strings.

In this project: Applied at inference on every call. Eliminated structural errors entirely.

03

Deterministic postprocessing

After the model returns, run code that fixes known deterministic failures: sort labels, canonicalize event names, strip hallucinated classes, add classes the model dropped.

Use when: You know the exact failure patterns — they repeat every time.

In this project: ~500 lines of postprocess rules. Doubled accuracy on some categories. The final fix that took 68% → 100% on the exhaustive suite.

Build order

Prompt first, grammar second, postprocess third. Postprocess is the last mile that turns 90% into 100% for known failures. Do NOT try to make the model “just be right.” Accept that models hallucinate and postprocess it deterministically.

Decision → Why

Chosen: all three layers, in that order. The prompt carried the domain rules, grammar made invalid structure impossible, and postprocess resolved the class-level failures that kept repeating. We stopped trying to persuade the model to be correct and started engineering the output contract around it.

Q4

Where do I get training data?

Four options, ranked by cost:

01

Human annotation

~$0.50–5.00 per example

Highest quality, highest cost. Use when the task is critical or subjective.

02

Teacher model distillation

$0–50 for hundreds of examples

Generate examples from a larger model (GPT-4, Claude, NIM, etc.). Quality depends on teacher. Validate before training.

03

Template-based generation

Free

Programmatically combine fields (e.g., 28 classes × 8 phrasings × 4 environments = 896 examples). Use when the input space is enumerable.

04

Synthetic with rules

Free

Template base + rules for variation + noise injection. Use for classifiers with structured labels.

In this project: Combined (2) + (3). Template-generated 538 inputs with varied phrasings per class, then NIM teacher produced the target outputs. Then validated + fixed with deterministic rules.

!

Key insight: The teacher’s mistakes become the student’s mistakes. Always validate the teacher’s output before training. We caught ~30% errors in the first pass (v1, 269 examples) and ~5% in the second pass (v2, 538 examples with more varied phrasings).

Decision → Why

Chosen: template-generated inputs plus NIM-generated targets, then deterministic validation. Human labeling was outside the budget, and raw templates lacked the linguistic variety the model needed. The teacher supplied natural phrasings; the validation pass prevented teacher errors from becoming training data.

Q5

How do I test before deploying?

Three test types, in this order:

Type AA

Exhaustive coverage suite

Deterministic tests, one per class, environment, and edge case. ~50–100 tests. Check: “Does the model know every category?”

In this project: 73 tests (28 classes, 20 environments, 10 multi-event, 5 silence, 5 no-class, 5 special rules).

Result100% after postprocess
Type BB

Novel phrasing regression

100+ inputs the model has never seen, phrased differently from training. Check: “Does the model generalize?”

In this project: 107 tests across 21 categories.

Result84% true accuracy — only after accounting for GT errors
Type CC

Ground-truth quality audit

Manually verify the teacher’s outputs on 20–30% of the regression set. You will find errors — teacher models are 5–15% wrong.

In this project: Found 9–10 of 107 NIM outputs were wrong.

ResultRaw “68%” became 84% true accuracy after correction
Critical lesson

Never ship based on one test type. Type A proves coverage. Type B proves generalization. Type C reveals that your “ground truth” is not actually ground truth.

Decision → Why

Chosen: exhaustive coverage → novel-phrasing regression → ground-truth audit. Coverage catches missing categories; regression exposes memorization; the audit prevents you from grading the student against a flawed answer key. Reporting only raw regression accuracy would have hidden both the teacher’s errors and the model’s true performance.

Q6

Local vs Cloud vs Hybrid deployment?

Option ALocal

Local deployment

Use when: Privacy is required, internet is unreliable, latency matters, or long-term cost matters.

Requirements: 8+ GB RAM (for 3B), 16+ GB RAM (for 7B), GPU optional but 5–10× faster.

Cost: $0 inference cost, but hardware cost.

In this project: Deployed via llama-server on Windows, ran at 7–8 tok/s on CPU.

Option BCloud

Cloud deployment

Use when: Zero hardware, per-token budget is acceptable, or you need the biggest possible models.

Cost: $0–50/month depending on volume.

In this project: NVIDIA NIM used as the primary annotation pipeline. Also as the teacher for training data.

Option CHybrid

Hybrid — recommended

Recommended for most teams.

Primary: Cloud API for high-quality, high-volume work (NIM, GPT, Claude).

Fallback: Fine-tuned local model for offline use, sensitive data, or cost reduction.

In this project: NIM as primary (10/10, 4s/clip), 3B local as fallback (100% exhaustive, 20–30s/clip).

Decision → Why

Chosen: hybrid. NIM gave the best per-clip quality and speed when the network was available; the local 3B gave offline coverage, privacy, and zero marginal cost. Keeping both meant the team never had to choose between highest quality and a usable fallback.

Q7

Which inference engine?

Inference engines, when to use each, and their role in this project
EngineUse whenIn this project
llama.cpp Best for GGUF files, CPU + GPU, runs on almost anything. Use when deploying quantized models to laptops, edge devices, or cheap servers. Local inference foundation. The server binary was used for CPU-only local deployment.
llama-cpp-python Python bindings for llama.cpp. Use when you need to call llama.cpp from Python. Used by the standalone annotation script.
llama-server OpenAI-compatible HTTP server (part of llama.cpp). Use when you need an API endpoint for coding agents (Pi, OpenCode) or custom UIs. Used for agent integration and local API access.
Ollama Wrapper around llama.cpp with a built-in model manager. Use when you want one-command install and don’t need fine control. Skipped because we needed explicit control over quant selection and grammar constraints.
vLLM High-performance serving engine. Use when you need to serve many concurrent requests (10+ users) on a GPU. Overkill for single-user local. Not used; this was a single-user local workload on CPU.
Unsloth Fine-tuning library + GGUF export. Use when training LoRA / QLoRA. Fast, memory-efficient, produces clean GGUF files. Training + export.

In this project: llama.cpp (server binary), llama-cpp-python (script), Unsloth (training + export), llama-server (agent integration). Skipped Ollama because we needed explicit control over quant selection and grammar constraints.

Decision → Why

Chosen: llama.cpp + llama-cpp-python + llama-server, with Unsloth for training. This stack supported GGUF, CPU inference, exact grammar control, and a local OpenAI-compatible endpoint without adding a model manager or a GPU-serving dependency. vLLM was overkill for one user; Ollama hid the quantization control we needed.

Q8

How do I quantize the model?

GGUF quantization types, and their impact on quality versus size:

GGUF quantization types, approximate quality, size, and deployment guidance
TypeQuality vs FP16Typical sizeUse
FP16 16-bit Baseline 2× Q8 Rarely used for deployment.
Q8_0 8-bit ~99.5% ~7 GB for 7B Use for archival.
Q6_K ~99% ~6 GB for 7B Rarely worth it over Q5.
Q5_K_M ~98.5% ~5 GB for 7B Good balance for GPU deployment.
Q4_K_M Chosen ~97–98% ~4.5 GB for 7B · ~1.9 GB for 3B Standard for local deployment. Best quality/size ratio.
Q3_K_M ~95% ~3.5 GB for 7B Use when RAM is tight.
Q2_K ~85% ~2.8 GB for 7B Visible quality loss. Use only as last resort.

In this project: Q4_K_M. The right call for 3B on an 8 GB laptop. Never go below Q3_K_M for production use — the quality loss is real.

Decision → Why

Chosen: Q4_K_M. It brought the 3B model down to about 1.9 GB while retaining roughly 97–98% of FP16 quality — enough to fit the laptop’s usable RAM and run on CPU. Lower quants traded away real semantic accuracy; higher quants added memory without a meaningful benefit for this narrow task.

Q9

How do I get the model into production?

Four deployment patterns, from simplest to most robust:

1 · Standalone script

Simplest

brioche_annotate.py loads the GGUF, runs inference, prints results.

Use when: Single user, annotation-only.

2 · Local HTTP server

Shared

llama-server provides an OpenAI-compatible API at 127.0.0.1:8080.

Use when: Multiple tools need to share the model.

3 · Web UI

Human-friendly

A FastAPI proxy wraps the API in a browser UI.

Use when: Users want copy buttons, batch mode, history, and no terminal.

4 · Hosted endpoint

Distributed

Hugging Face Spaces, RunPod, or Vast.ai exposes a remote API.

Use when: The team is distributed or users lack hardware.

In this project

All four. Python script for single-clip work. llama-server for Pi/OpenCode. FastAPI UI for browser annotation. Hugging Face for private artifact hosting.

!

Key insight: Match the deployment to the user’s workflow. Annotation work needs a fast CLI or web UI, not an agent interface. Coding agents (Pi, OpenCode) fight the fine-tuned behavior because they inject their own system prompts.

Decision → Why

Chosen: every layer, each pointed at a different workflow. The script serves one-off annotation, llama-server shares the model with local tools, the FastAPI UI serves non-terminal users, and Hugging Face hosts the private artifact. The important boundary is that the fine-tune is not a general-purpose agent; production annotation belongs behind a controlled interface.

3 The full journey

Chronological, including the paths that did not work. The order matters: each phase changed the hypothesis for the next one, and several “model problems” turned out to be prompt, data, or integration problems.

01

Prompting
Goal
Get working annotations without any training.
Tried
OpenCode + Claude, then NVIDIA NIM (Nemotron 3.5 Bolt E4B hosted).
Result
10/10 on reference cases with NIM. Built a Streamlit web UI. ~4s/clip.
Why not stop
Zero cost, but tied to a hosted API. No offline mode. Rate limits at scale.
LessonA good teacher model + carefully engineered prompt + grammar constraints gets you 90% there. The last 10% requires data.

Model choice

03

Phase 3 — Dataset generation

Data
Goal
Create enough training data without human labeling.
Approach

v1 · 269 examples

Template-generated. 100% validated. But model only got 6/10 — data wasn’t diverse enough.

Training
Approach
LoRA fine-tuning on Qwen 3B using Unsloth on Kaggle T4.

Phase 7 — Integration attempts (learning what NOT to do)

Dead end
Approach
Verify Pi and OpenCode can use the model as an agent.
Result
They can, but shouldn’t. Pi and OpenCode inject their own coding-agent system prompts, which override the annotation fine-tune. The model starts behaving like a chatbot and may hallucinate tool calls.

4 The repeatable pipeline

The ten-step process for building a small specialized model. The order is deliberate: do not train until the task is specified, the teacher is verified, and the data is clean.

  1. 01

    Step 1 — Define the task precisely

    Write down the exact input format, output format, and validation rules. If a fresh annotator couldn’t do it from your spec, the model can’t either.

  2. 02

    Step 2 — Verify a teacher model can do it

    Test GPT-4 / Claude / NIM / largest available model on 10–20 cases. If the teacher can’t reach ~90%, the task is too hard or the spec is ambiguous.

  3. 03

    Step 3 — Design the system prompt

    Include the taxonomy, rules, edge cases, worked examples. Test with the teacher. Iterate until the teacher hits ~95%.

  4. 04

    Step 4 — Generate a diverse template of inputs

    For each class, write 5–10 genuinely different phrasings (not variations of “loud X”). Include multi-event combinations. Include edge cases (silence, no-class events).

    Target: 500–600 inputs for ~30 classes.
  5. 05

    Step 5 — Generate target outputs with the teacher

    Run the teacher on all inputs. Save as JSONL. Record timing and model name.

  6. 06

    Step 6 — Validate the teacher’s output

    Check structure (all fields, valid enums), semantics (labels match events), and consistency (same input always same output).

    Target: 100% clean data. If not, either improve the prompt or patch with deterministic postprocess.
  7. 07

    Step 7 — Fine-tune a small model

    LoRA / QLoRA on Qwen 2.5 3B (or 1.5B for simpler tasks). Unsloth is the fastest path. ~20–30 min on a T4 for 500 examples.

  8. 08

    Step 8 — Test exhaustively

    • 50–100 deterministic tests covering every class / environment / rule
    • 100+ novel phrasings the model hasn’t seen
    • Manually review the ground truth — you will find teacher errors
    Gates: If exhaustive < 95%, patch with postprocess. If novel phrasing < 80%, you have a data variety problem, not a model problem.
  9. 09

    Step 9 — Export and package

    Merge LoRA into base. Quantize to Q4_K_M. Export GGUF. Bundle with:

    • The exact system prompt used during training (TRAIN_SYSTEM.txt)
    • The exact postprocess code (postprocess.py)
    • A runnable script (annotate.py)
    • A README explaining install and accuracy
    Artifact bundle layout from Step 9

    The model is not the artifact. The bundle is. Ship the contract and the runtime with the weights.

    brioche-qwen3b-annotator-v2/
├── brioche-qwen3b-Q4_K_M.gguf   # quantized weights
├── TRAIN_SYSTEM.txt             # exact system prompt used in training
├── postprocess.py               # deterministic output repair
├── annotate.py                  # runnable local runner
└── README.md                    # install, usage, measured accuracy
  10. 10

    Step 10 — Deploy and monitor

    Archive the GGUF privately. Deploy locally via llama-server or via a FastAPI web UI. Log every annotation to JSONL. Review failures weekly. If a new failure pattern emerges, patch postprocess before retraining.

The pipeline rule

Do not retrain to fix a deterministic bug. Retraining is for generalization failures. Missing tags, canonicalization, enum cleanup, and known disambiguations belong in postprocess because they are reproducible and testable.

5 Failure modes catalog

Every failure we encountered, why it happened, and the fix. Use this as a diagnostic index: start with the symptom, not the tool.

Failure modes, causes, fixes, and examples from the project
# Failure Why it happened Fix Example / lesson
01 Empty labels for a common class
hum → []		 Model too small; prompt rule missed the specific phrasing. Add explicit mapping to the system prompt + add the class in postprocess. hum → HVAC was fixed by adding an explicit mapping to the SYSTEM prompt.
02 Wrong but related class
dog-whining → dog-barking		 Adjacent classes in the taxonomy are visually similar in embedding space. Add disambiguation rules + worked examples for the pair. “Dog whining → Dog Whining / Howling, NOT Dog Barking” as a rule.
03 Hallucinated classes outside the taxonomy Grammar constraints weren’t applied; the model tried to “help” by inventing. Grammar-constrained decoding with Literal[28 strings] enum. Effect: structural errors dropped to 0%.
04 Dropped classes on multi-event inputs Model says “Talking, Footsteps” in sound_events but only tags Talking. Postprocess detects event keywords in sound_events and adds missing classes. “footsteps” in events → add “Footsteps / Movement” if not present.
05 Wrong environment
rain + thunder → indoor-active		 Model interprets “rain and thunder” as noisy, ignoring the “indoor” keyword. Explicit system-prompt rule: rain/thunder are SOUNDS, not environments. Also force env from input keywords in postprocess. The input’s explicit environment keyword outranks inferred acoustic intensity.
06 Generic assistant response instead of annotation Agent framework (Pi, OpenCode) injected its own coding system prompt. Use a standalone script; never use the fine-tuned model as an agent. Lesson: the system prompt at inference time must match the system prompt at training time.
07 Model invents a source
e.g. “paper rustling”		 Model over-specifies; the source-neutral rule wasn’t enforced. Add rule: “use neutral label unless source is clearly identified in input.” Postprocess strips over-specified variants. Prefer the neutral class until the input gives enough evidence to choose a source-specific class.
08 Wrong class on substring
“wind howling” → Dog Whining		 Postprocess rule matched “howling” without checking for dog context. Postprocess rule requires BOTH the keyword AND context (“dog” must appear). Keyword-only rules manufacture false positives. Add context conditions.
09 Out of memory on 8 GB laptop Model (1.9 GB) + context (500 MB) + other apps (Chrome 2 GB) > 3.7 GB available. Close Chrome before starting. Cap context at -c 2048. Accept the constraint. Memory pressure is a deployment constraint, not a model failure.
10 Very slow inference
30s instead of 15s per clip		 Not enough free RAM → swap thrashing. Close other apps. Confirm ~3 GB free before starting. Speed returns to normal. Check available RAM before benchmarking speed; the model can be fine while the machine is thrashing.
11 Hugging Face 401 Unauthorized Repo is private, token expired, or the hf_... placeholder was not replaced. Regenerate token with Write permission; use hf auth login; verify with api.whoami(). Authenticate deliberately and verify identity before debugging the upload code.
12 Fails on taxonomy-adjacent inputs
duck quacking, crow cawing		 These aren’t in the training data — duck, crow, seagull, pigeon, horse aren’t in the Brioche taxonomy. Postprocess recognizes these as no-class; OR expand the taxonomy if needed. Lesson: any model has a boundary. Know where yours is, document it, and use postprocess to guard it.
How to read this catalog

First classify the failure: structural, semantic, environmental, integration, operations, or taxonomy boundary. Then fix it at the cheapest layer that can enforce correctness. Grammar for structure. Prompt examples for ambiguity. Postprocess for deterministic repetition. New data or a larger model only when the failure is genuinely one of generalization.

Template 2 — Validation rules for teacher output

Run this checklist against every generated record before the data is allowed into training. Structural checks are cheap; semantic checks are the ones that protect the student.

View the validation checklist 3 layers 
For each generated record, check:

STRUCTURAL:
  - All required fields present
  - Field types correct (list, string, enum)
  - Enum values from allowed set only
  - Label ordering rules respected
  - Deduplication applied

SEMANTIC:
  - Each class label maps to an event in the input
  - Environment matches input keywords
  - Speech flags consistent with events
  - Special rules applied (e.g., media ≠ music, baby crying ≠ speech)

CONSISTENCY:
  - Same input → same output
    (run teacher 2x on 10 inputs, check for identical results)

    parsed = json.loads(text)
    labels = parsed["Brioche_Class_Label"]
    events = parsed["sound_events"].lower()
    inp_l = inp.lower()

    # Fix: [WHAT TO CHANGE]

    # Rule: [DESCRIPTION]
    # Also strip hallucinated classes

Template 4 — Exhaustive test suite structure

One deterministic test per class, environment, and rule. This suite proves coverage; it does not prove generalization.

View the exhaustive test skeleton Python 
tests = [

Template 5 — Regression test structure

Use unseen phrasings and assert the full expected output, not only one label. Keep the ground truth manually audited.

View the regression test skeleton Python 
cases = [
    # (input, expected_labels, expected_env)
    ("hum indoor env", ["HVAC / Fan / White-Noise Hum"], "indoor-quiet"),

Template discipline

A template is not a shortcut around the specification. The rules inside it are the actual product. Change the taxonomy and the rules must change with it; change the teacher and the examples must be re-audited.

Stack logic

The stack was chosen for control at the boundaries: Unsloth for training speed, llama.cpp for low-memory CPU inference, llama-quantize for a standard artifact, llama-server for an OpenAI-compatible endpoint, and FastAPI for a controlled human interface. 9 What we’d do differently

Reflections on the process, not just the outcome. The model shipped, but several detours were avoidable — and the lessons are in the detours.

01

We should have built the postprocess earlier.

We spent hours trying to make the model “just be right” through prompt engineering. Postprocess would have fixed most failures in 30 minutes.

Lesson: when failures repeat, postprocess them — don’t retrain.

02

The v1 dataset (269) wasn’t diverse enough, and we could have seen this earlier.

“Loud snoring” and “quiet snoring” are one pattern, not two. “Loud snoring” and “nasal snoring” are two. The v2 dataset succeeded because we deliberately varied the vocabulary, not because we added 269 more examples.

03

We over-trusted NIM as ground truth.

The 107-case regression revealed 9–10 NIM errors. If we’d manually reviewed 30 NIM outputs before designing the test, we’d have known the ceiling was ~92% and set expectations accordingly. Always audit your teacher.

04

The 95% target on novel phrasing was unreachable.

100% minus 8% GT error = 92% ceiling. 95% was mathematically impossible. We should have set the target at “reach the GT ceiling” instead of “reach 95%.”

Lesson: know your ceiling before you measure against it.

05

We iterated on the wrong lever (model size) before the right one (data variety).

0.5B → 1.5B → 3B each doubled data-following, but the biggest jump came from v2’s varied data on the same 3B model. Model size helps, but data variety matters more for narrow tasks.

06

We should have packaged the bundle on day one.

The HF push happened last, after the model was final. In hindsight, every intermediate version should have been pushed — it would have been free insurance against session loss and easier to iterate.

07

The Pi/OpenCode integration was a detour.

It took time and proved nothing useful — the models’ system prompts fight the fine-tune. A standalone script was the correct interface from day one.
